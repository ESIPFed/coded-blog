Benchmarking IPFS as a resilience layer for cloud-optimized geospatial data (Zarr · Icechunk · xarray)
Cory Levinson  ·  Rich Signell  ·  Brian Terry
★ An ESIP Funding Friday Project

Objective

Decentralized storage networks like IPFS have offered content-addressed, location-independent data access for over a decade. Meanwhile the geoscience community has converged on cloud-optimized formats — Zarr, and now Icechunk — that make huge environmental datasets readable through efficient chunk-level range requests.

CODED asks one practical question: can IPFS serve as a resiliency layer for cloud-optimized geospatial data — and what are the real performance trade-offs?

Approach

  • Published a 500-hour ERA5 2-m air-temperature slice (2.08 GB logical, 500 Zarr chunks) to IPFS via Kubo.
  • xarray.open_zarr() reads directly over an IPFS gateway — no code changes, just point at the CID.
  • Benchmarked the identical dataset three ways: Icechunk on S3, IPFS HTTP gateway, and a local IPFS daemon over Bitswap.
  • All three return a bit-identical result (area-weighted mean = 286.5062 K) — verifying correctness alongside speed.

Bottom Line

IPFS works as a resilience layer — and the access path is everything. An HTTP gateway co-located with the data delivers S3-class throughput (even beating native S3 here).

But cold peer-to-peer Bitswap replication across a high-latency link is glacial. Front your IPFS node with a regional gateway, and content-addressing buys you verifiable, takedown-resistant data either way.

The Singapore Test

Tuning Bitswap

Raising the Kubo chunker from 1 MiB to the 2 MiB ceiling cut blocks-per-chunk from 4 → 3, reducing Bitswap round-trips over the Pacific link.

Even so, Bitswap stayed ~23× behind the HTTP gateway — the gap is session-management overhead, not block size.

What This Means

  • Gateways win for consumers. Reading through any HTTP gateway in the data's region gives S3-class (or better) throughput with zero code changes.
  • Cold P2P replication is slow over high-RTT links with a single peer — budget ~1 MB/s; more peers and tuning help.
  • Resilience holds regardless. Content-addressing + pinning keeps datasets verifiable and alive as nodes come and go.
